# M27 系统内核换自建宿主 —— 三个内核一套按钮、一套手势

- 状态：已落地（等上机验收）
- 时间：2026-10-11
- 触发：用户问「mpv 与系统播放器上面的按钮显示及功能显示统一了吗」—— 答案是**没有**：
  系统内核的画面一直是 `AVKit.VideoPlayer`，控件与手势归系统（M02P15 起的老口径），
  M26 那套按参考重排的按钮只长在自绘内核（MPV / 自研 FFmpeg）上。用户拍板：统一（「开工」）。

## 一、做法：把系统内核的画面也换成自建宿主

| 层 | 改法 |
| --- | --- |
| 画面层 | `CatVodPlayer/SystemVideoSurface.swift`（新）：一层 `AVPlayerLayer` —— 与 `MpvVideoSurface` / `FFmpegVideoSurface` 同一套路（引擎与界面都持有、生命周期比会话长） |
| 引擎 | `AVPlayerEngine` 持有 `videoSurface`（建实例时把播放器挂上去）；`setScaleMode` 从空实现改成写 `layer.videoGravity` |
| 宿主视图 | `CatVodUI/Platform/SystemVideoView.swift`（新）：`UIViewRepresentable` / `NSViewRepresentable`，挂层逻辑与另外两个内核共用 `LayerHostView` |
| 播放页 | `PlaybackView` 的 `@State player: AVPlayer?` 换成 `systemSurface`；画面区 / 控制条 / 手势的判定从「自绘内核」改成「有画面层」（`hasVideoSurface`）—— 系统内核从此和另外两个内核走**同一条**控制条（`PlaybackView+Controls`）与**同一套**手势（`PlaybackView+Gestures`） |

三个内核的差异只剩「内核真做不到的」：

| 项 | 系统 | MPV | 自研 FFmpeg |
| --- | --- | --- | --- |
| 画面比例 | 适应 / 裁剪铺满 / 拉伸铺满（M27 新） | 全部五档 | 三档 |
| 视轨 | 无（没有公开 API，不摆） | 有 | 无 |
| 音频增益 | 无（`AVPlayer.volume` 封顶 1） | 有 | 有 |
| 画中画 | 有（M27 新，见下） | 不做（要帧拷贝层） | 不做 |

## 二、画中画：从「系统的」变成「我们的」

M26 第四批的结论是「system 内核的 PiP 由系统控件提供」。换掉 `VideoPlayer` 之后那颗系统按钮没了 ——
PiP 自己起：`AVPictureInPictureController(playerLayer:)`（公开 API），落在
`CatVodUI/Platform/PlaybackPip.swift`：

- 顶排多一颗「画中画」（参考同位置）；`isPictureInPicturePossible` / `isPictureInPictureActive`
  用 KVO 盯着（Apple 官方 PiP 自定义播放器样例就是这么做的），按钮的可用态与图标跟着走；
- `canStartPictureInPictureAutomaticallyFromInline = true`：切后台 / 按 Home 时系统自己起 PiP
  （M26 第四批那套「后台出声」的体验由它接上）；
- 换内核 / 离开播放页时停掉并拆掉（`detach()`）—— 别让 PiP 挂在一个已经拆掉的内核上；
- macOS 这一版不做（留个空壳类型让播放页两端共用）；设备不支持时整颗按钮不出现（UI 规范第 5 条）。

## 三、口径与取舍

- **UI 规范第 1 条（原生优先，不为统一观感自绘系统控件）管的是「系统控件」**：导航 / 列表 / 弹窗 /
  搜索栏这些照旧全部交给系统。播放页的控制条是**本项目自己的产品设计**（M26 按参考版式定下、三个内核共用），
  不是对 AVPlayerViewController 控件的仿制 —— 换宿主是「把画面交到自己的层上」，不是「重画系统控件」。
  （规范里补了这句注。）
- **放弃的**：系统播放器自带那套控件与手势（AirPlay 按钮、系统进度 / 音量条、系统手势）——
  这正是「统一」的定义。AirPlay 路由本身没丢：`AVPlayer` 的外部播放默认开着，系统控制中心仍可投
  （M26 第七节的投屏结论不变：播放器里那颗投屏按钮不做）。
- **没做的**：自绘内核（MPV / FFmpeg）的 PiP（要一条逐帧拷贝层，M26 第六节拍板不做）；
  macOS 的 PiP；投屏按钮。

## 四、验证点（模拟器 / 真机）

- 三个内核各播一次：画面上都是**同一套**控制条（顶排 ✕ / 投屏（仅系统）/ 旋转 / 画面比例 ——
  画中画（仅系统）/ 弹幕 / 倍速 / 锁；底排徽标 + 时间 / 进度 / 播放 / 下一集 +
  播放器 / 字幕 / 视轨 / 片头片尾 / 选集（音轨两条以上才多一颗））；
- 手势三家一致：单击显隐、双击暂停、横拖进度、左右半屏纵拖亮度 / 音量、长按加速、捏合缩放、上滑下一集；
- 系统内核：画面比例三档当场见效；顶排「画中画」起 → 小窗播放 → 点回来退出；切后台自动起 PiP（设备支持时）；
  换到 MPV 内核后「画中画」这颗**消失**（能力只在做得到的内核上出现）；
- 全屏（TMDB 视图点播放）与精简视图顶上那块（16:9 槽位）：系统内核也是我们这条控制条，✕ 能关；
- 就地放大（M27 首验之四）：精简视图播起来 → 点 ⤢ —— 画面**当场变大**（不黑、不重载、进度不断）
  并转横屏；✕ = 收回那块继续播 + 翻回竖屏；
- 控制条三套版式，动作一致：**精简视图竖屏 = 极简版**（徽标 / 进度 / 播放暂停 / 右下角全屏，
  见第五节追记之二）；横屏 / iPad = 文字按钮（对齐参考）；竖屏全屏 = 图标按钮（放不下就换版）。

## 五、追记（2026-10-11 首验录屏）

录屏里两个真 bug，都在精简视图顶上那块槽位：

1. **槽位塌成小框**：点「百度原画」（type=3/4）的集时，顶上只剩一个几十 pt 的小黑框
   （转圈 + 「正在向站点请求播放地址…」）—— 槽位尺寸原来靠内容 `.aspectRatio` 提议，
   而转圈 / 文案这类内容**自带固有尺寸**，报多大就是多大（与坑 30 同一族）。现在**尺寸由黑底说了算**：
   `Color.black` + 16:9 定尺，内容铺在 `overlay` 上 —— 三种形态（直链 / 站点换地址 / 海报占位）都跟着黑底走。
2. **底排文字按钮被压成「播…」「…」**：六颗文字按钮（播放器 / 字幕 / 视轨 / 音轨 / 片头片尾 / 选集）
   在竖屏（~390pt）放不下（宽版要 ~541pt）。现在**窄了换图标版**（`playerControls(width:)`，
   分界线 560pt）：横屏 / iPad 维持文字（对齐参考），竖屏换图标，动作与菜单内容一模一样
   （播放器 `play.rectangle` / 字幕 `captions.bubble` / 视轨 `rectangle.on.rectangle` /
   音轨 `waveform` / 片头片尾 `bookmark` / 选集 `list.bullet`）。
3. **不算 bug、但要知道**：百度原画那集起播后画面黑了 ~5 秒（进度照走）—— 那是「软解 4K
   （徽标里的 `SW`）+ 模拟器」的起步时间；真机 / 硬解另算（与 M04P2 的 HDR 验收同一条挂账）。

**追记之二（2026-10-11 首验截图）**：精简视图**竖屏**只要「参考里圈住的那几样」——
参数徽标 / 进度 / 播放暂停 / 右下角那颗「全屏」；其余按钮**全部**去全屏那层（那层始终完整）。

- `PlaybackView` 多一个 `minimalControls`（精简视图顶上那块传 true，经 `destination(...)` /
  `SitePlayEpisodeView` 透传）；
- 极简版只在**竖屏**生效（宽度 < `barCompactWidth`）：横屏下那块槽位恢复完整版；
  全屏那层（TMDB 点播放 / 槽位点 ⤢）**从不**进极简版；
- 原来在顶排的那颗「全屏」挪到极简版的**右下角**（参考同位置）；点它顺手把屏幕翻成横屏
  （iOS 16+ 公开 API；翻不了就不翻），全屏那层的按钮始终完整；
- 顺手把 `+Controls` 的菜单与小件拆去 `PlaybackView+BarMenus.swift`（`+Controls` 的类型体
  又贴到 `type_body_length` 450 的 error 线，与 `+Speed` / `+Tracks` 同一套做法）。

**追记之三（2026-10-11 · 全屏按参考图对齐）**：用户给了一张参考全屏截图，照它改：

- 顶排顺序对齐：关闭（✕）· **投屏** · 旋转 · 画面比例 —— 画中画 · 弹幕 · 倍速 · 锁定；
  「画面比例」图标换 `aspectratio`（斜箭头留给「全屏」那颗）、「倍速」换 `speedometer`；
- **投屏**（新，只有系统内核）：`AVRoutePickerView`（公开 API：系统音频路由 + AVPlayer 外部播放）——
  这颗本来就是系统内核**原先就有**的能力（原来长在系统播放器自带的控件里，M27 换自建宿主之后没了，
  这里接回来）；MPV / 自研 FFmpeg 没有公开的路，整颗不出现（DLNA 的结论见 M26 第七节，不变）；
- 底排对齐：参数徽标 / 进度 / 播放暂停 · 下一集 —— 播放器 · 字幕 · 视轨 · 片头片尾 · 选集。
  参考图里**没有**「逐帧」与独立「音轨」两颗：「逐帧步进」从控制条撤掉（功能还在引擎里，入口待定）；
  「音轨」收成**两条以上才出现**（只有一条时菜单里是「自动 + 那一条」，等于没得选 —— 不摆没用的开关）；
- 「全屏」那颗定死在动作行的**最右**（就地那块两套版式都在右下角）；全屏那层没有它（参考图里也没有）。

**追记之四（2026-10-11 · 就地放大不再换播放器）**：精简视图里点控制条那颗 ⤢，原来是「拆掉就地这块、
**换一层新的播放器**」（`fullScreenCover` + 新建引擎）—— 用户看到的是黑一下、重新拉流 / 重解析
（站点集还要重新换地址），一句「旧的播放器状态又显示出来了」。现在改成**同一块画面就地放大**：

- `isInlineExpanded`（详情页状态）：true = 只留播放器铺满整屏（`aspectRatio(nil)` + `ignoresSafeArea(.all)`）、
  下面的详情收掉、导航栏藏起来（新基础件 `adaptiveNavigationBarHidden`，macOS 空操作）；
- **播放器一个字节都不重建**（同一个 `PlaybackView` / 引擎照旧在跑）：进 = 放大 + 翻横屏
  （那颗 ⤢ 里顺手做的）；出（✕）= 收回那块（**接着播**）+ 翻回竖屏；
- 放大后控制条回**完整版**（`minimalControls: !isInlineExpanded`）—— 那边要 ✕ 才能收回来；
  同时那颗 ⤢ 不再出现（已经全屏了，不摆没用的开关）；
- TMDB 视图那条路不变（点播放 = 从头进全屏那层）。

**追记之五（2026-10-11 · 放大后不成方屏）**：用户截图 —— 精简视图点 ⤢ 放大 + 转横屏之后，
画面是一块**正方形**，上下露着页面白底。根因：`Color.black.aspectRatio(nil, contentMode: .fit)` 里的
`nil` 不是「不限比例」，而是「按视图**自己的固有比例**」——`Color` 的固有比例是 1:1，槽位就被定成方的。
（追记之四里写的「`aspectRatio(nil)` = 不定尺」是错的，此条更正。）

改法：高度**自己算**，不再交给 `aspectRatio`：

- 常态：`width / compactPlayerAspect`（16:9）—— 宽度由 `compactLayout` 新增的一层 `GeometryReader` 量出来；
- 放大（`isInlineExpanded`）：高度给 `nil` —— SwiftUI 里「跟着父级铺满」的是 `frame(height: nil)`，
  不是 `aspectRatio(nil)`；再配合 `ignoresSafeArea(regions, edges: .all)` 铺满整屏。

`compactPlayer` 相应改成 `compactPlayer(width:)`。

**追记之六（2026-10-11 · 就地放大后画面还是旧槽位 + 点按失灵）**：用户截图 —— 点 ⤢ 之后黑屏是铺满了，
但画面还是**旧槽位**那么大、锚在左上角，点屏幕别处没反应；再一会儿「2.0x」一直亮着、点按全不动了。
两处毛病、两份账：

1. **宿主视图没跟着长**（画面小在左上角）：`LayerHostView` 是 `UIViewRepresentable` 的视图，而
   `UIView.sizeThatFits(_:)` 的默认实现返回**视图已有的尺寸** —— SwiftUI 拿它当「这个宿主想要多大」，
   于是布局变了（就地放大 / 转屏 / 分屏 / 换槽位）之后，画面还停在**上一个尺寸**上。
   用户截图里的数与它完全对得上：可见画面 395×165 —— 2.39:1 的片按 402 宽 fit 出来的，
   而 402×226 正是**竖屏那块 16:9 槽位**的尺寸。
   - **首验没修好**：先只写了 `sizeThatFits(_:)`（提议多大就是多大）+ `autoresizingMask`，
     画面照样卡在旧槽位 —— 因为**框架压根不再问它**：`UIViewRepresentable` 的尺寸
     **只在「视图的值变了」时才更新**，而 `surface` 这个值在布局变化时根本不变。
   - 真正的修法：**把尺寸明文递进去** —— 画面区（`GeometryReader`）量出来的 `size` 塞进三个宿主
     视图的值里（`SystemVideoView(surface:size:)` / `MpvVideoView(surface:size:)` /
     `FFmpegVideoView(surface:size:)`），值一变 `updateUIView` 就会被调到；
     `LayerHostView.attach(_:sizedTo:)` 收到尺寸后自己 `frame = (0,0,size)`，
     并把层的 `frame` 也定成这个尺寸（`syncFrame` 优先用递进来的尺寸，没有才退回 `bounds`）。
   - 外面再包一层 `.frame(width:height:alignment: .topLeading)`：手势层（`contentShape`）跟着铺满
     （不然「点屏幕别处没反应」还会剩），画面锚在画面区左上角。
   - 两条保险都留着：`sizeThatFits` 覆写（框架要问就给对的）+ `autoresizingMask` 跟着容器长。
   三个内核共用这一个宿主视图，所以这一处修的是三家。
2. **长按加速会「挂死」**（一直 2x + 点按失灵）：SwiftUI 的手势被系统取消时（转屏 / 视图重建 /
   控制条显隐这类布局变化都会）`onEnded` **不发**，`isSpeedBoostHolding` 就一直挂着 ——
   一直按长按倍速在播、提示一直亮「2.0x」，而且 `shouldSwallowTap()` 会吞掉之后**每一次**点按。
   用户看到的「一点播放区域就自动 2 倍速，再点就没反应了」就是它。修法：
   - 新常量 `speedBoostTrustSeconds`（1.5 秒）：「还按着」只信这么久 ——
     正常松手补发的那次点按在 0.3 秒内就到（单击要等「双击优先」那一下），1.5 秒绰绰有余；
   - 判定收成纯函数 `tapDisposition(isHolding:holdStartedAt:endedAt:now:)`（有单测）：
     吞 / 放行 / **挂太久 = 先收加速再放行**（顺手恢复用户那份倍速，并清掉「刚松手」的标记，
     别把恢复后的连点也吞掉）；
   - 再兜一条：画面区尺寸一变（`onChange(of: proxy.size)`）就把加速收掉 ——
     布局变了，那次长按多半已经被系统取消了。

## 六、教训 / 坑

- **换掉系统控件是「改口径」不是「加功能」**：老口径（M02P15 起）写在 `docs/UI 规范.md` 与一堆任务记录里 ——
  这类改动先把代价讲清楚（失去系统原生控件与手势）再动手。
- `AVPictureInPictureController(playerLayer:)` 在 SDK 上是 failable 初始化器；写成
  `let created: AVPictureInPictureController? = AVPictureInPictureController(playerLayer: layer)`
  两种签名下都编得过（本机没编译器的稳妥写法）。
- 层宿主两边都要：`SystemVideoView` 的 iOS / macOS 分支与另两个内核一模一样 ——
  共用 `LayerHostView`，不要各写一份挂层逻辑。
