# M28P13 搜索再快一点 · 切站点用缓存 · 封面并发抬到 8

- 状态：**已改**（本地闸门全绿）；上机观感等用户确认
- 时间：2026-10-12
- 触发：用户报「影视的搜索速度可以再加快一点；发现页切换站点后站点的加载速度可以加快；
  各站点封面的加载速度也可以快点」。

## 一、搜索：缓存那份「先上墙」改成**跨全部可搜站点**去找

原先先吐的那份缓存只查**首轮那 ≤12 个站点**（`firstRound.map(\.key)`）。而缓存命中常常落在别的
站点上 —— 首轮没搜到、补搜轮才搜到的那些：那种情况下「重搜同一部片」还是得等网络，等于白做。

现在：拿**全部可搜站点**的缓存（`SiteKey + 关键词`，≤10 分钟），命中就立刻上墙，并且把它们
**计入「参与」**（`searchedKeys`）—— 墙上立刻有内容，`enoughHitSites`（3）也立刻够数，
整轮搜索几秒内收口、不再跑补搜轮。没缓存的站点照旧按第一轮 / 补搜轮的路径走。

（这也是「从已经缓存的站点搜索」那条用户口径的补全：缓存不分首轮/补搜轮。）

## 二、发现页切站点：先吃缓存，没有再联网

`.onChange(of: selectedSiteKey)` 里写死的是 `loadHome(force: true)` —— 而首页缓存与分类缓存
**都是按站点 key 存的**：写死 force 等于每次换站点都要重新打两趟站点接口（首页 → 分类，**串行**），
换回刚看过的站点也一样。这就是「切换站点后加载慢」。

现在改成 `loadHome()`（不带 force）：换回缓存还在有效期内的站点时，分类条与首屏**秒开**；
缓存过期（「首页缓存时间」）或没缓存时照旧联网；要强制拿最新有下拉刷新那条路（它仍是 `force: true`）。

## 三、封面：每个 host 的并发连接 4 → 8

`ImageLoader` 的会话原来限「每个 host 4 条连接」—— 发现页/详情页一屏就是十几张**同源**封面
（很多图床同 host），4 条意味着「4 张一批」地铺。抬到 8（浏览器同主机的惯用上限也是 6~8 这一档）：
铺得更快，又不至于把图床打疼。内存/磁盘缓存的语义一字未动（缓存命中还是 0 网络）。

## 四、验证点

1. `swift test --package-path Packages/CatVodUI`（搜索「先吐缓存那份」那条用例的语义不变：
   缓存站点仍在第一份 outcome 里）；
2. 上机：
   - 搜同一个词两次：第二次应当**秒出**（哪怕上次的命中来自首轮之外的站点）；
   - 发现页切到刚看过的站点：分类条 + 首屏应当秒开；切到没看过的站点照旧要等网络（那是站点接口的账）；
   - 发现页/详情页封面：一屏铺满的速度应当更快（缓存命中仍为 0 网络）。
