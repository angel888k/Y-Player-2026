# M28 播放控制设置 —— 手势可配 + 控制中心 + 震动（对齐参考的「播放控制」页）

- 状态：已落地（等上机验收）
- 时间：2026-10-11
- 触发：用户给参考 App 的「播放控制」两张截图 ——
  「播放控制设置里改成这样的功能，且能统一控制所有播放器的全屏的控制」。

## 一、这一页现在有什么（逐行对齐参考）

| 分组 | 行 | 落点 |
| --- | --- | --- |
| （第一组） | 默认倍速 | `PlaybackSpeedBook`（老线 M03P12/M03P13，与播放页滑杆共用同一把存档） |
| | 长按倍速 | 同上（2.0–5.0、步进 0.5） |
| | 快进 / 快退步长 | `PlaybackControlSettings.seekStepSeconds`：10 / 15 / 30 / 60 秒，默认 15 |
| | 控制中心显示 | `Platform/PlaybackNowPlaying`（`MPNowPlayingInfoCenter` + `MPRemoteCommandCenter`） |
| | 自动识别片头片尾 | `autoOpeningEnding`：开播跳「片头」、播到「片尾」自动下一集 |
| 单击手势 | 单击屏幕中间 / 两边 | 显示 / 隐藏控制条（默认）、播放 / 暂停、快进 / 快退、无 |
| 双击手势 | 双击屏幕中间 / 两边 | 默认播放 / 暂停；选「快进 / 快退」时**左半屏退、右半屏进**，步长取上一项 |
| 滑动手势 | 音量 / 亮度 / 进度 / 短剧滑动切集 | 各一条开关：关掉的手势整次不做事（不提示、不改值） |
| 震动反馈 | 长按屏幕 / 滑动调亮度 / 音量 / 进度 | `Platform/PlaybackHaptics`；每跨 1% / 1 秒震一下（`PlaybackHapticGates`） |

## 二、口径

- **三个内核算一套**（M27 的延续）：偏好只有这一份（``PlaybackControlSettings``），
  播放页**进页时读走** —— 与「播放内核 / 解码方式」同一口径（M24P1）：正在播的那一页不中途换手感。
- 存档一把键 `yplayer.playbackControl`（15 个字段竖线拼接）；**坏存档整体回落默认**
  （字段数不对 / 认不出的动作 / 非数字步长都算坏）。默认值 = **M28 之前的行为**（回归基线，有单测钉住）。
- 「中间 / 两边」的分区与「纵甩切集」共用一条：中间一半 = 宽度的 1/4 … 3/4，两侧四分之一 = 两边 ——
  手上不按屏幕分区，规则就必须是同一份（`PlaybackSwipeRules/isCenterZone`）。
- **落点怎么来的**（iOS 15 也吃）：`TapGesture` 不给位置、`SpatialTapGesture` 要 iOS 16+ ——
  在画面层上挂一条**零距离拖动**记起点（公开 API），点按与拖动照旧各走各的。
- 控制中心发布的是**能确知的四项**（剧名 / 时长 / 进度 / 状态）+ 三条命令（播放·暂停 / 上一集 / 下一集）。
  没有播放列表（直播 / 下载播放 / 设置页试播）就不注册上 / 下一条；**画中画在播时让路**
  （那一份归系统，两边一起发就是两份信息打架）。位置事件**同一秒只发布一次**。
- macOS：控制中心与震动这一版都不做（`isSupported` 为假 → 对应行 / 整组不出现），
  与画中画同一口径（产品目标在 iOS）。

## 三、验证点（模拟器 / 真机）

1. 设置 → 播放器 → 播放控制：五组都在；改一项退出再进，值还在（重启 App 也还在）。
2. 把「单击屏幕两边」改成「播放 / 暂停」→ 播放页点画面两侧：暂停 / 继续；点中间仍是显隐控制条。
3. 把「双击屏幕两边」改成「快进 / 快退」→ 左半屏双击 = 退 15 秒、右半屏 = 进 15 秒（提示条显示目标时间）。
4. 「滑动调节进度」关掉 → 横拖不做事（也不出提示）；「短剧滑动切集」关掉 → 中间纵甩不换集
   （音量 / 亮度那两条照旧）；把四条都关掉再逐条打开，确认互不影响。
5. 震动开关：关掉的那一条不震，开着的每跨 1% / 1 秒震一下（**真机才有**；模拟器不震是正常的）。
6. 控制中心：进播放页 → 下拉控制中心 / 锁屏：剧名 + 进度在；按暂停 / 下一集能回到播放页生效 ——
   **系统内核、MPV、自研 FFmpeg 各试一次**（三个内核同一份）。
7. 自动识别片头片尾关掉 → 有片头标记也不跳、播到片尾标记不自动下一集（标记还留着，也能手动标）。

## 四、取舍 / 遗留

- 「自动识别片头片尾」的**识别**本身不做（音频指纹那类；上游也没有 —— M03P16 已拍板）；
  这一项管的是「**自动用**已标的两个点」。
- 手势设置**进页时读一次**，不做播放中热更新（与内核 / 解码同一口径）。
- 控制中心在**画中画在播**时由系统那一份接管（我们让路）—— 上机时顺手确认两者不会打架。
- 「长按屏幕」「双击」这些动作本身不变（长按 = 临时加速，M03P12），这一页只加**开关与落点**。

**追记之一（同一轮 · 位置事件的界面节流）**：用户报「正常播放中偶尔顿一下」。查下来两条：

- MPV 的 `time-pos` 是**按帧**观察来的（每秒几十条 `timeChanged`），而播放页每收一条就把
  位置 / 时钟 / 进度条一起刷一遍 —— 一秒几十次全页重建（系统内核本来就每秒一条，不受影响）；
- 修法：``PlaybackClock/isSampleDue`` —— 界面按 **0.1 秒**踩一个采样点（10Hz）；
  覆盖层的顺滑照旧靠 `time(at:)` 外推（它的注释里写的正是这件事），不靠事件频率。
- 还剩一个疑点没钉死：模拟器上 MPV 是软解 + MoltenVK，解码本身的分量有多大没量过 ——
  若节流之后还顿，下一手是把**原始事件率 / 丢帧**打一条日志再判（不先猜）。

**追记之二（同一轮 · 全屏 UI 拉齐：系统内核也报播放信息）**：用户问「所有播放器全屏时的 UI 显示统一了吗」——
逐项对照下来，三个内核在**同一部片**上的差别只剩两处，都在这一轮收掉：

1. **底排徽标 / 「播放信息」区**：MPV 与自研 FFmpeg 报得出，系统内核一个字都没有（M04 当年的结论是
   「`AVPlayer` 给不出这一套」）。其实 `AVFoundation` 报得出画面 / 编码 / 帧率 / 色彩 / 码率 / 音频
   这几项 —— 公开 API、读的是媒体自带的元信息。新增 `SystemPlaybackStats`：
   从 `AVAssetTrack`（异步属性）/ `CMFormatDescription`（四字码 + 色域 / 传输函数扩展）/
   `accessLog`（HLS 实时码率）/ URL 后缀（容器名）拼成**与另外两个内核同一套原始键**，
   走同一个 `PlaybackStats` 文法；色域 / 传输函数那份「标签 → 名字」映射**复用自研内核的**
   （`LibavVideoDecoder.colorPrimariesName` / `transferName`），不两处各写一份。
   - 系统读不到的**三项不硬造**：硬解路径（`AVPlayer` 不暴露解码器）/ 丢帧 / 转换后的输出 ——
     那三行在界面上不出现，徽标里也就没有 `HW/SW`；
   - 容器名只认 URL 后缀（系统没有 demuxer 名可读），认不出就不写那一行。
2. **视轨菜单**：原来只要有一条就出现（MPV 会报出唯一的那条）—— 与音轨那条「两条以上才有得选」
   的规矩不一致。改成 `videoTracks.count > 1`：普通片子三个内核都不摆这一颗，多视频轨的片源里
   MPV 才出现。

对完仍然**做不到统一**的（都是能力差，写在各自的表里）：系统没有「硬解 / 软解」读数、没有丢帧读数、
外挂字幕只有 MPV / 自研内核吃（系统只吃内嵌）、画面比例系统与自研三档而 MPV 五档。

**追记之三（同一轮 · 点屏幕没反应 + `2.0x` 常亮：旁听手势又坑了一次）**：用户报「点击屏幕没反应、
显示不了功能按钮，还有一个 `2.0x` 显示」。根因就是**为「中间 / 两边」分区记落点**加的那条
**零距离拖动**（`simultaneousGesture(DragGesture(minimumDistance: 0))`）：

- 它看着「只记位置、不参与动作」，可**照样进手势竞争** —— 这正是 M02P16「坑 28（旁听手势会吃掉
  滚动）」的同一类；首验的症状是点按被吃掉（单击不触发 → 控制条叫不出来），
  长按加速那条序列被打断（`onEnded` 不来 → `isSpeedBoostHolding` 挂着 → 提示一直亮 `2.0x`、
  连点按也一起被吞）。
- 修法：**落点由点按手势自己给** —— 新增基础件 `Platform/AdaptiveTap.swift`：
  iOS 16+ 用 `SpatialTapGesture`（`value.location`），iOS 15 回落 `TapGesture`（落点 nil →
  按「中间」那一档处理）；设置页在 iOS 15 上**不摆**「屏幕两边」两行（不摆点了没反应的开关）。
- 教训（与坑 28 合并记）：**播放页上不要再挂任何「旁听」手势** —— 要什么信息就用那件事自己的手势拿，
  拿不到就按能用的那一档处理。

**追记之四（同一轮 · 全屏手势再扫一遍：别再让「界面自己」把长按弄死 + 排障留痕）**：用户报
「还是有问题」。把全屏这条链路从头扫了一遍，除了上面那条旁听拖动，还揪出**三处会让手势死的
自伤**（都是「一次视图树结构变化把正在识别的手势取消」，M27 记过这一类）：

1. **长按加速的提示自己把自己取消**：`beginSpeedBoost()` 写 `gestureHint` → 提示条那个
   `if !gestureHint.isEmpty { … }` **挂进来** → 结构变化 → 那次长按序列被取消 → 松手永远不来。
   修法：提示条**常挂在视图里**，只翻不透明度（空文本时 opacity 0）—— 一进一出改成只改内容。
2. **控制条自动收起**：按住期间如果正好到 4 秒，控制条一收 = 结构变化 = 同一刀。
   修法：`beginSpeedBoost()` 把自动收起的计时**掐掉**，松手时 `endSpeedBoost()` 按当前状态补排
   （新 `refreshControlsForState()`，与「状态变化」那条共用一份判定）。
3. **状态变化里无条件 `showControls()`**：一边按着一边缓冲（网络流很常见）就会把控制条亮出来
   → 又是结构变化。修法：`consume` 的状态分支加一句「按着的时候先别动控制条」。
4. **拖动那条自愈**：挂着的长按状态原来会把**整条拖动**挡掉（`onChanged` 直接早退），只能靠
   再点一下才恢复。修法：拖动守卫改用 `isSpeedBoostHoldingTrusted()`（与点按共用同一把
   `tapDisposition` 尺子）—— 挂太久就当那次长按已被吞掉，收加速、放行这次拖动。
   （不会误伤正经的「按住加速」：按住不动时拖动本来就不触发。）

再加两件排障用的：

- `Platform/PlaybackTrace.swift`（`.notice` 级）：**每一次点按**（单击 / 双击、落点、分区、按设置
  解析出的动作；被吞掉 / 锁上没做也都记）、**长按加速的起与收**、**控制条显隐是谁改的**。
  「点屏幕没反应」再出现时，一条命令就能看出断在哪一段：

      xcrun simctl spawn booted log show --last 5m --predicate 'subsystem == "com.YPlayer.cat"' --style compact | grep playback

- 「播放控制」页加一颗**恢复默认（全部手势与控制）**：万一把某一区设成了「无」又忘了，
  一键回出厂 —— 也让「点了没反应」有一个明确的出口。

**追记之五（同一轮 · 日志把「点屏幕没反应」钉死了：长按阈值太低 + 尾巴吞得太多）**：用户带回的
`playback` 日志（M28 首验之四加的那条）一眼看出两件事：

1. **每一次「单击」前面都跟着一条「长按加速 起 2.0x」** —— 用户自然的单击按到 **0.6–0.7 秒**
   （按得实一点 / 在瞄准点哪儿），而长按线是 0.5 秒：于是每一下「单击」都被吃成长按，
   随后补发的那一下点按又被「长按尾巴」吞掉 —— 这就是「点屏幕没反应」；
2. **「收」总比松手晚 0.5–1 秒**（`onEnded` 那条路就是慢），所以 `2.0x` 提示会多亮一会儿。

修法（四条时间线一起重排，全在 `PlaybackView+Gestures`）：

| 线 | 原值 | 现值 | 为什么 |
| --- | --- | --- | --- |
| `speedBoostHoldSeconds`（起加速） | 0.5 | **0.8** | 0.5 秒会把「按得实一点的单击」（实测 0.6–0.7 秒）吃成长按 |
| `speedBoostSwallowHoldSeconds`（吞尾巴，量出来的） | —（原来一刀切全吞） | **1.3** | 只有真·长按（实际按住 ≥ 1 秒）的尾巴才吞；0.8–1.0 秒那一档放行 |
| `speedBoostTrustSeconds`（「还按着」的信任窗） | 1.5 | **3.5** | 真·长按可以按很久（日志里就有 1.6 秒的），1.5 秒会把真实按住错判成挂死 |
| `speedBoostSwallowSeconds`（松手后的尾巴窗） | 0.5 | 0.5（不变） | 仍在，但现在只对「真·长按」生效（用 `endedAt - holdStartedAt` 量一遍） |

外加两条「不靠 `onEnded`」的保险（它慢、还可能不来）：

- **点按即松手证明**：点按只在松手后才解析 —— 所以点按一进来就把加速收掉（提示立刻消失、
  速度回原样），不等那条 `onEnded`；
- **收完把「刚松手」窗口清掉**：那一下就是尾巴本身，别再让它吞掉下一个真点按（日志里
  「吞尾巴」那条规则会顺带把后面的连点也吞掉，就是这个窗口被重新武装了）。

**追记之六（同一轮 · 「吞尾巴」只在控制条亮着时做 + 把按住时长写进日志）**：把全屏这条链路
又从头扫了一遍（画面层 / 三个叠层 / 控制条 / 手势链 / 提示条，逐个看 hit-testing 与判定），
结论：

- **三个叠层（弹幕 / 字幕 / 提示）都关着 hit-testing**（`allowsHitTesting(false)`），控制条的
  压暗底同样关着 —— 点按不会被它们吃掉；手势链的顺序与 M27 那套一致（点按 → 长按 → 拖动 → 捏合），
  没有新的「旁听」手势；
- 真正还能让「点屏幕没反应」复现的只剩一种组合：**控制条本来就暗着 + 这次按住够长（被吞）** ——
  那正是最难受的一种（怎么按都不出来）。所以「吞尾巴」这条规则再加一个前提：
  **只在控制条亮着时吞**（吞的目的本来就是「别让它闪一下」）；暗着的时候这一下照常执行 ——
  用户按屏幕十有八九就是要把它叫出来。
- 把**判定输入写进日志**：点按日志多一段「距长按起 X.XXs」（没长按则写「无长按」）——
  下一轮排障不用再靠推算用户按了多久；顺手补了「拖动被打断时也收掉提示」（提示条改成常挂之后，
  不清就会一直挂在屏上）。
