# M28P6 精简视图切全屏「有时候黑屏」：VO 重建没认下就再建一次

- 状态：**已改**（本机闸门全绿 + 新单测）；**现场日志还没拿到** —— 见第四节的「如果还黑」
- 时间：2026-10-12
- 触发：用户报「精简视图竖屏播放后切全屏有时候会黑屏，应该是 mkv 格式，所有播放器所有格式都检查一遍」。

## 一、先把三个内核这条链复核一遍（用户要求「所有播放器都检查」）

| 内核 | 画面层 | 布局变化（转屏 / 就地放大）时谁管尺寸 | 结论 |
| --- | --- | --- | --- |
| 系统（AVPlayer） | `AVPlayerLayer`（`SystemVideoView`） | 层自己跟 bounds | 历史那次「画面钉在左上角」是**宿主尺寸没递进去**，M27 已修（尺寸明文递进 `LayerHostView`） |
| 自研 FFmpeg | `AVSampleBufferDisplayLayer`（`FFmpegVideoView`） | 同上；渲染侧对 `failed` / `requiresFlushToResumeDecoding` 有 flush 兜底（`LibavVideoRenderer`） | 布局路径不重建层；「有声音没画面」那类有日志可查 |
| MPV | `CAMetalLayer`（`MpvVideoView`） | **没人替它管**：`--wid` 窗口尺寸不自己变 —— 要转告 `window-size`，不认就**重建 VO** | 本次动的就是这条（下面） |

容器格式（mkv 等）本身与布局无关：三个内核都是「解出来再画」。用户看到的「mkv 才黑」更可能是
**那类片源走的是 mpv / 自研内核 + 大尺寸**，所以这次盯的是「尺寸 → 重建 → 认下」这条链。

## 二、已知的两个洞（本次修掉）

1. **重建没认下 = 黑屏，而且不会自己好**：`vo=null` → `vo=gpu-next` 之后如果 mpv 没在 500ms 内
   认下新尺寸，原来只记一条日志就完了 —— 而那种情况很可能就是「VO 没建起来」：画面全黑、
   没有任何东西会来救它。现在：等半拍 → **先确认一次**（上一拍可能只是慢，认下就不白拆）
   → 还没认下就**再建一次**（同一个会话才认，换片 / 换内核之后作废）。日志里会多
   `，重试 1 次后认下 = 是/否`。
2. **起播时尺寸可能一条都没报过**：`onChange(of: proxy.size)` 只报「变化」——
   引擎建起来时尺寸已经稳了的话（`.onChange` 早跑过、而那时 `engine` 还是 nil），mpv 永远拿不到
   这个尺寸，会一直按它建 VO 那一刻的窗口出画。现在 `PlaybackView` 记住画面区当前尺寸，
   起播后**补报一次**。

## 三、验证点（Mac / 模拟器）

1. `swift test --package-path Packages/CatVodPlayer`：`MpvEngineTests` 里三条与 VO 重建相关的用例
   按新行为更新（假会话从不认 → 一次重建 + 一次重试），并新增
   「重建没认下会重试一次」；
2. 上机（重点在**之前黑屏的那台系统版本 + 那些 mkv**）：精简视图竖屏播放 → 点 ⤢：
   转屏动画里画面应当跟过去；万一没跟过去，**半秒内应当自己回来**（日志里一条
   `已重建 VO（… ms，认下 = 否，重试 1 次后认下 = 是）`）。

## 四、如果还黑：发我这几行日志就够定位

```bash
xcrun simctl spawn booted log show --last 5m --predicate 'subsystem == "com.YPlayer.cat"' --style compact   | grep -E '画面区|重建 VO|自愈探针|Metal 画布|宿主尺寸|显示层'
```

- `画面区 …（点 …）`：尺寸有没有报进来、报了几次；
- `已重建 VO（…，认下 = …）`：重建有没有认下、重试有没有救回来；
- `自愈探针：…`：mpv 自己会不会认（决定下一步是「等它」还是「别拆 VO」）；
- 自研内核还需要 `显示层 failed` / `显示层要求 flush` 那两行（`LibavTrace`）。

有这些就能区分三种可能：重建失败（本次已加重试）、尺寸没报（本次已补报）、
以及「mpv 这条路根本不该拆 VO」（那要换 render API，属于另一笔）。
