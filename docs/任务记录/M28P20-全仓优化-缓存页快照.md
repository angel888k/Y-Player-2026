# M28P20 全仓优化 · 第二批：缓存管理页的占用数字改「快照」

- 状态：**已改**（本地闸门全绿）；上机验证随下次构建
- 时间：2026-10-12
- 触发：同 M28P19（全仓扫描），这轮盯「每渲染一次的重复 IO」。

## 一、病灶

`SettingsCacheView`（设置 → 数据 → 缓存管理）原来把四个缓存占用写成 **AppModel 的计算属性**，
而这些属性每次取值都会**遍历目录**（`enumerator` + 每个文件的 `resourceValues`）。页面每重建一次：

- 图片那一份要枚举 **4 遍**：两行「清空」的可用态 + 「全部缓存」+ 说明区文案；
- 源 / 首页 / 节目单各枚举 2~3 遍（行、全部缓存、说明区各来一次）。

图片目录是几千张小文件（缓存管理页打开时通常正是缓存攒得最大的时候）——
页面越「有料」，进页面和每次状态变化时的卡顿越明显（同样是「看得见、清得掉」的用户口径，
数字本身没错，错在**算得太勤**）。

## 二、修法

- 页面持有 `CacheSizeSnapshot`（`@State`）：四个口径一次算好（两份 summary + 两个字节数），
  行与说明都读它；
- 重算时机：**进页面**（`.task`）+ **每次清空之后**（含「清理其他接口残留」）—— 别的时机数字不会变；
- 模型侧 API 一字不动（`sourceCacheSummary()` 等照旧，测试也在用）；数字口径与展示文案不变。

## 三、验证点

- `swift test --package-path Packages/CatVodUI`（`ImageCacheWiringTests` / `LiveEPGCacheWiringTests`
  走的就是模型 API，未受影响）；
- 上机：把图片缓存攒大后再进「设置 → 数据 → 缓存管理」——页面应当**瞬时打开**、滚动顺；
  点任意「清空」后数字立即归零。
