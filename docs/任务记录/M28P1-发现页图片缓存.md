# M28P1 发现页滑动卡顿：图片管线（内存 + 磁盘缓存 / 去重 / 下采样）

- 状态：**已实现**（本地闸门全绿 + 新单测；上机待验）
- 时间：2026-10-11
- 触发：用户报「发现页各站点各列表滑动卡顿不流畅」。

## 一、根因（代码层）

「各站点各列表都卡」是结构性问题，不是某个源的数据问题。全 App 的图都走 `AsyncImage`
（`DiscoverViews` / `HomeView+Data` / `LibraryRows` / `LiveView` / `VodDetailView+Compact` / TMDB 三处），
它有三个叠加的拖累：

1. **没有内存缓存**：列表滚动时卡片被回收、滚回来重新构建 —— `AsyncImage` 会**重新发起请求 + 重新解码**，
   一屏海报就能把滑动拖成顿挫；
2. **解码在主线程、按原始尺寸解**：图床给多大的图就整张展开多大（几百 KB 的 4K 海报展开成
   几十 MB 位图），主线程被解码占满，帧就掉在这里；
3. **没有同 URL 去重**：同一张图被两处同时要（分区横滑与纵向网格重叠、详情页与列表重叠）会各下一份。

## 二、做法

新增 ``ImageLoader``（`CatVodUI`，M28 首验之二十九）：

- **内存缓存**（`ImageMemoryCache`，actor）：解码后的 `UIImage`（已下采样）按
  「URL + 目标尺寸」缓存，NSCache 按像素 cost 超限回收；
- **HTTP 磁盘缓存**：`URLCache`（256 MB）落在 `cacheDirectory/Images`，新鲜度按服务器的
  `Cache-Control` —— 与「设置 → 缓存管理」的清缓存口径一致；
- **在途去重**：同一个 URL 只跑一个 `Task`，按等位计数；等的人全走了（滚动回收）就取消下载，
  下载不白跑；只要还有人在等，发起者的取消不牵连其他人；
- **下采样**：`ImageIO` 的 thumbnail 解码在后台线程做，主线程只拿成品；
- ``CachedImage``（SwiftUI 视图）替换 `AsyncImage`：命中缓存**同步出图**（滚回去不闪占位），
  失败留占位色不弹错；目标尺寸 = 外层明文（横滑卡 112pt / 缩略图 60x84 / 频道图标 34x34）
  或布局提议（纵向弹性网格用 `GeometryReader` 现算）。

替换的调用点（第一轮）：发现页海报卡（横滑 + 纵向网格）、``VodRow``、``PosterThumbnail``、
直播频道图标、精简视图海报占位。TMDB 三处（详情头图 / 匹配面板 / 海报集）**故意没换**：
它们用的是 `AsyncImage` 的 phase 分支（HDR 与失败态各画各的），换要连着改观感，单独立项。

## 三、缓存管理接线（用户口径）

缓存全部要「看得见、清得掉」——「设置 → 数据 → 缓存管理」新增：

- **「图片缓存数据」一行**：显示占用（`imageCacheByteCount`），点「清空」二次确认后清
  （`clearImageCache()`：删磁盘目录 + 清内存缓存 —— 只删盘的话进程内那层会把已删的图继续吐出来）；
- **「全部缓存（大小）」把它算进去**（`totalCacheByteCount` 四处之和）；「清空全部」也一起清
  （`clearAllCaches()` 因此变 `async` —— 图片那份要连带清内存）；
- 说明区补「图片缓存」的当前占用。

## 四、故意没做

- **不预取**（按可见范围提前下几张）：内存缓存已经解决「滚回去重下」；预取的收益与复杂度
  （滚动方向 / 提前量）留到上机量出「首次加载还是顿」再做；
- **不动 TMDB 三处**（见上）；
- **不换源的图床策略**（服务端给多大的图我们管不了）：冷缓存首屏仍然是一次真下载，
  缓存只保证「第二次起不重下」。

## 五、验证点（Mac / 模拟器）

1. `swift test --package-path Packages/CatVodUI`：新增 `ImageLoaderTests`（缓存命中不再发请求、
   并发只发一次、下采样到目标内、清缓存后重新下载、非法地址快速失败）与
   `ImageCacheWiringTests`（占用合计 / 清空返回数 / 接线目录）；
2. 上机：进发现页滚动一个列表来回几遍 → 「设置 → 数据 → 缓存管理」里「图片缓存数据」的大小
   应当涨到一个稳定值（说明真的有存量、不是每次重下）；点「清空」后归零、回到发现页图重新加载；
3. 观感：滑动不再一顿一顿（重点看滚回去的那几屏 —— 原来会闪白重下）。


## 六、收尾（2026-10-11）：卡顿的**真根因**与定案

图片管线这一轮（内存 + 磁盘缓存 / 去重 / 下采样）本身是独立收益，但「滑动卡顿」的**主因**不是它 ——
是一路排查后靠**帧账**定死的另一件事，记在这里免得下次再走一遍弯路：

**现象**：发现页滑动一顿一顿；模拟器（Mac mini / iOS 26）上帧账双峰 ——
要么 `8~17 帧 · 中位 16ms · 超 0 帧`，要么 `2 帧 · 中位 150ms`。

**隔离实验**（一次构建、App 内切档，逐层排除）：
- 卡片纯色块 / 去导航链接 → 仍卡（图片与 `NavigationLink` 排除）；
- 整页换 200 个纯色格的裸网格 → **顺**（滚动容器本身无罪）；
- 去掉滚动监听器（滑动收 Tab 栏那条线）→ **顺**；
- 去掉下拉刷新 → 仍卡（`refreshable` 无罪）。

**定案证据（重建计数 × 帧账）**：`scrollBody` 每次求值 +1、拖动结束出账 ——
**0 次重建的拖动全顺，1~2 次的就卡（每次重建 ≈ 50~100ms）**。根因：`HomeView` 持有收放状态
（先是 `@State`，换成 `@StateObject` 也只降到 1~2 次/拖动），**只要门归 `HomeView` 所有，
它一广播 `HomeView.body` 就整体重来** —— 一屏 `LazyVGrid` + `NavigationLink` 的 diff 在模拟器
上就是 50~100ms。

**修法**：收放的「门」`DiscoverTabBarGate` 改成**静态共享**（`DiscoverTabBarGate.shared`），
没有任何视图持有它，唯一观察者是 `BookTabBarHider` 那一层 —— 收放只重算那一层，滚动内容
一次都不再求值。**修复后帧账：全场 `中位 16ms · 超 24ms 0 帧`、重建 0 次。**

顺带落地/保留：
- `ScrollFrameProbe`（拖动回调节拍记帧）与 `ImageLoadTrace` 保留 —— 零成本、模拟器限定，
  下次再有「滑动/加载不对」直接有账；
- 诊断脚手架（档位开关 / 重建计数 / 对照网格）**用完即拆**；
- 图片管线继续覆盖剩余调用点：TMDB 头图 / 匹配面板 / 剧照卡片也换 ``CachedImage``。

**已知边界**：模拟器（Mac mini）的性能不代表真机；帧账 16ms 只说明「模拟器上不掉帧」，
真机观感仍以用户实测为准。


## 七、追记：左上角「站点切换」菜单的弹出卡顿（2026-10-11）

同一批排查的余波：用户报「发现页左上角点开那一下卡」。诊断链路与滚动那条同款：

**判定**（一次构建的对照实验）：把菜单临时换成「最小形态」（两颗固定项、无清单无子菜单）
—— **明显更顺** ⇒ 剩余手感是**内容量**造成的，不是系统菜单不可优化。

**收口**（逐条都是「菜单里每多一项/一层，弹出的建树就更沉」）：
- 主清单从全量 → **前 8 行 + 当前站点**（被截在外面自动补一行，永远能找到自己），
  余量给一行「还有 N 个 —— 用『查找站点…』」（该入口本来就是为长清单准备的原生搜索栏 + 全量列表）；
- 「重命名站点 → 全量」两级子菜单 → 一颗扁平的「重命名当前站点…」（要改谁先切到谁）；
- 「分组排序」从主菜单常驻 → 「更多」子菜单，且**只在分组 > 2 时出现**（两行动作不值得白占一层）；
- 分组筛选**跨开合记忆**（`HomeView.siteGroupFilter`）：选过一次某组，之后菜单只列那一组。

**已知边界**：模拟器（Mac mini）上，贴近这个规模的原生菜单弹出仍有「一点点」系统底噪
（同尺寸最小菜单也有）；真机观感以用户实测为准。诊断用的「最小菜单」开关在收口时已撤。
