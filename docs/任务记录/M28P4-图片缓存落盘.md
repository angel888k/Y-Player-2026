# M28P4 图片缓存「看不到有缓存」：字节层自己落盘

- 状态：**已修**（本机闸门全绿 + 新单测；上机待验）
- 时间：2026-10-12
- 触发：用户报「缓存管理中的图片缓存应该是有问题的，看不到有缓存」。

## 一、根因：磁盘那份一直不存在，而它存不存不归我们管

图片的磁盘缓存原来**完全交给 `URLCache`**（`cacheDirectory/Images`）。而 `URLCache` 存不存
由**响应头**说了算：`Cache-Control: no-store` / `private`、或者压根没给缓存头的图床，
一张都不会落到盘上 —— 上游那批图床里这种不少。于是：

- 内存缓存（`ImageMemoryCache`）在起作用（所以滚动是顺的），但它是**进程内**的，重启就没了；
- 磁盘上确实什么都没有 → 「设置 → 数据 → 缓存管理 → 图片缓存数据」永远是 0 / 「清空」灰着，
  看着就像坏了；
- 顺带一个隐患：`Cache.db-shm` / `Cache.db-wal` 这两个**活的** SQLite 附属文件原来没被认成
  「`URLCache` 自己的」，既被算进「可清占用」，清空时还会被删掉 —— 等于在别人写库时抽走一半账本。

## 二、修法

| 文件 | 改动 |
| --- | --- |
| `CatVodUI/ImageFileCache.swift`（新） | **字节层**磁盘缓存（actor）：拉到的原始字节按 URL 存 `<md5(url)>.img`，读会 touch（LRU），容量 256 MB 超了先删最久没读过的；`removeAll` 只删自己的 `*.img` |
| `CatVodUI/ImageLoader.swift` | 取图顺序改为**内存 → 磁盘字节 → 网络**；网络拿到的字节落盘；解不出的坏字节当场删掉（不然会成为负缓存）。`clear()` 连带清这一层 |
| `CatVodUI/AppModel+ImageCache.swift` | `Cache.db` **全家**（`Cache.db` / `-wal` / `-shm`）都算「`URLCache` 自己的」：不计入可清占用、清空时不删 |

收益：**缓存管理里看得见、清得掉、重启还在**（下一次启动首屏的图直接从磁盘读，不再整批重下）；
同一张图给两种目标尺寸用时只下一次、解两次（尺寸仍各自成条，`ImageLoaderTests` 盯着这条）。

## 三、有意没做

- **不把内存缓存算进「图片缓存数据」**：它是进程内的，算进来会出现「刚重启就显示有缓存」的假象；
  「全部缓存」同样只算磁盘。
- **不做「按尺寸存字节」**：字节与尺寸无关，按 URL 存一份就够（解码再按尺寸各来一次）。
- **不换 `URLCache`**：它仍然是 HTTP 那层（协议缓存 / 重定向 / 304 语义），这一层只补它兜不住的部分。

## 四、验证点（Mac / 模拟器）

1. `swift test --package-path Packages/CatVodUI`：新增 `ImageFileCacheTests`（往返 / 跨尺寸共用 /
   只删自己 / 超容量淘汰 / 读会 touch）；`ImageLoaderTests` 改两条（两种尺寸只下一次、
   新实例走磁盘不再发请求）；`ImageCacheWiringTests` 加 `Cache.db` 全家那条；
2. 上机：进发现页来回滚几屏 → 「缓存管理 → 图片缓存数据」应当**真的涨**（不再是 0）；
3. 点「清空」→ 数字归零、回发现页图重新加载；再滚一遍又重新涨；
4. 杀掉 App 重开、进发现页：图片应**直接出**（磁盘命中，不再整批重下）—— 日志里 `ImageLoadTrace`
   的 ok 条目会少一批。
