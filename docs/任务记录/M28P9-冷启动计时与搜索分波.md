# M28P9 冷启动分段计时 · 聚合搜索分波 · 「从头播放」接着播

- 状态：**已改**（本地闸门全绿 + 新增一条纯函数用例）；冷启动的实测耗时等用户回一次日志
- 时间：2026-10-12
- 触发：用户报「1. 接口已经导入过的情况下冷启动加载感觉有点慢；2. 全屏播放器的播放控制等，
  有问题的进行修复；3. 搜索影视的速度还是慢」。

## 一、搜索慢（有实测数据，先修这条）

主接口（kstore 那类）的站点清单实测 **96 个站点**，其中 95 个是 js2p（`type=3`）站点，
且**一个都没标** `indexs` —— 于是「索引站点优先」那条回落规则退化成**首轮 96 个一起发**。
这 96 个请求的 `api` 全指向**同一个本机宿主**（`127.0.0.1:<port>`），而 `URLSession`
按 host 限并发（默认 6）：实际是 6 个一组排队跑，一波里混进几个慢站点（那个接口里好几个
站点 15 秒才超时）后面几组就全被堵住 —— 整面墙十几到几十秒才陆续有内容，这就是「还是慢」。

改法（两处，都是「别再一起挤」）：

1. `AggregateSearchRules.firstRoundLimit = 12`：首轮只取前 12 个站点（照站点清单顺序）；
   一个都没搜到时，补搜轮照旧把其余的搜完 —— **覆盖率不变**，只是第一轮先给人看。
2. `AppModel.searchRound`：一轮里也**分波**发（每波 12 个，波内并发、波间顺序）——
   补搜轮同样如此，每波都是「同时起跑、同时收尾」。
3. `AppModel.siteSessionConfiguration()`：站点请求的 `URLSession` 每个 host 并发连接
   抬到 12（默认 6），与首波数量对齐 —— 否则首波自己也要排两轮。

## 二、冷启动慢（先做能立刻省的 + 埋好计时）

- **能立刻省的一段**：`RootView` 的启动任务原来把「读配置（含起内嵌 Node 宿主，秒级）→
  起本机服务 → 恢复下载」**串着**跑 —— 后两件跟配置毫无依赖，白等。现在三件 `async let` 并着跑。
- **慢在哪一段得先看见**：新增 `Platform/StartupTrace.swift`（分类 `startup`），在
  `load()`（起点 / 配置已加载 / 恢复流程完成）与 `refreshHost`（宿主就绪 + 站点数）各记一条
  `启动：<段名> 累计 <ms>ms（附注）`。下一条命令就能看出 3 秒是花在宿主还是配置：

      xcrun simctl spawn booted log show --last 2m --predicate 'subsystem == "com.YPlayer.cat"' --style compact | grep 启动

## 三、全屏播放器的播放控制：修了一处真毛病

- **「从头播放」只 seek 不 play**（`PlaybackView+EpisodeFlow.restartFromBeginning()`）：
  这条路多是一集播完之后点的，而三个内核在 `ended` 之后 `seek` 回去都**不会自己再播**
  （AVPlayer 的 rate 还是 0、mpv 停在 EOF、自研内核停在结束态）—— 点下去画面停在 0 秒不动。
  同文件的 `loopCurrentEpisode()` 一直是 `seek` + `play`，这里补上后半句。
- 其余部分（顶排 / 底排 / 菜单 / 手势分派 / 锁屏 / 选集面板 / 进度条）本轮**逐段读过一遍**，
  没有找到新的可证缺陷；如果还有具体现象（哪一颗按钮、哪台系统版本），发一张截图，
  按截图改 —— 不再凭猜动布局。

## 四、验证点

1. `swift test --package-path Packages/CatVodUI`：新增「首轮截前 N 个：96 个站点的主接口不再
   「一次全发」」；旧的索引站点 / 临时禁搜等用例不变（都在 3 个站点以内，不受上限影响）。
2. 上机：
   - 搜索：新搜一个词，首波结果应几秒内出现（不再等几十秒才「搜完」）；
   - 冷启动：随手记一下从点图标到发现页出内容的时间，并把上面那条 `grep 启动` 的输出发我；
   - 播放页：播完一集后点「从头播放」—— 应当从 0 秒**接着播**，不再停在 0 秒。
